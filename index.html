DS-079 Ops

Define layout pattern recipes and card-min-width token

build

The container model (DS-008a) defines the page-level shape — centered max-width container with internal padding. What it doesn't define is how multiple items arrange WITHIN the container. Without column grid concepts, we need a named, finite set of layout pattern recipes that AI generates natively and that map 1:1 to Figma component names. Add to tokens/structural/layout.json (or a new tokens/structural/layout-patterns.json): • --layout-card-min-width: 280px — minimum card width threshold for repeat(auto-fill, minmax(...)) grids; determines when a card grid wraps to fewer columns. AI defaults to ~280px naturally. Add a new Storybook page (Foundations → Layout Patterns) documenting five recipes, each with reference CSS and Figma equivalent: 1. Stack — vertical with gap. flex column + gap. 2. Cluster — horizontal wrap with gap. flex row + flex-wrap + gap. 3. Sidebar — fixed-width sidebar + flex content. grid-template-columns or flex with basis. 4. Switcher — row above a threshold, column below. flex-wrap + flex-basis trick (no media query). 5. CardGrid — auto-fill minmax(--layout-card-min-width, 1fr). Each recipe gets a CSS class name (.ds-stack, .ds-cluster, etc.) intended to be mirrored as a Figma auto-layout component preset. The naming is the contract: designers pick a Figma component named 'Stack', AI writes a div with class 'ds-stack', they produce the same output. Patterns are based on Every Layout (every-layout.dev) primitives.

DS-080 Ops

Add section composition pattern + vertical section padding tokens

build

DS-008a defined the inner container model (centered max-width + horizontal padding). The model is incomplete for real page composition because AI builds pages as stacked full-bleed sections, each containing a centered container with vertical padding-block. Adding the section pattern closes this gap. TOKENS (add to tokens/structural/layout.json): • --layout-section-padding-compact: 48px — padding-block at smaller viewports (below the padding step). Aliases --spacing-xl2. • --layout-section-padding-default: 96px — padding-block at the padding step and above. Aliases --spacing-xxl3. • Step transitions at --layout-padding-step (768px), same boundary as horizontal padding for consistency. REFERENCE CSS PATTERN documented on the Layout System page: .layout-section { padding-block: var(--layout-section-padding-compact); } @media (min-width: 768px) { .layout-section { padding-block: var(--layout-section-padding-default); } } .layout-section > .layout-container { ... } /* nested container handles horizontal */ PAGE UPDATE — Foundations → Layout → Layout System: • Restructure into two stacked sub-sections: 'Container' (existing content) and 'Section composition' (new). • Expand Layout Tokens table to include the new --layout-section-padding-* values. • Add a second visualization showing stacked sections with their padding-block at 375 and 1440. • Update Reference CSS to show the full section + container composition pattern AI produces. • Update Tip — Figma frame strategy to mention designing full-height stacked sections, not just the container. RATIONALE: Container and section are the same architectural concern — page composition. Keeping them on one page preserves the unified mental model that matches how AI actually generates code. 2026-06-22 — Section vertical rhythm was initially attempted in DS-008a as `--layout-gap-section: 48px` (categorized as a 'gap' token). Pulled back because it conflates two different concerns: inline `gap` (CSS gap property, spacing between siblings inside a flex/grid container) vs section vertical rhythm (CSS `padding-block` on the section, or `margin-block` between sections). AI's mental model matches this split — `gap-2/4/6/8` for inline, `py-12/24` or `space-y-16` for section rhythm. This ticket owns the section side properly: define `--layout-section-padding-compact` and `--layout-section-padding-default` as `padding-block` tokens applied to section wrappers, NOT as gap tokens.

DS-081 Ops

Define breakpoint token scale (component-level) — decide between Marina-inspired and AI-aligned

build

DS-008a removed the breakpoints section from the Layout System page because breakpoints no longer drive container margins (container uses max-width + auto-centering instead). But AI still writes media queries at conventional breakpoints for component-level responsive behavior — type scaling, layout pattern shifts (CardGrid columns, Switcher threshold), nav collapse, etc. The DS needs a sanctioned breakpoint scale or AI will improvise. DECISION REQUIRED — pick a scale: Option A (Marina-inspired): 375 / 768 / 1024 / 1440 / 1920 Pros: matches Marina, matches typical Figma frame sizes (1440 = designer default), preserves prior decisions. Cons: 1440 sits awkwardly against the 1280 container cap. AI doesn't naturally produce 1440 / 1920 media queries. Option B (Tailwind / AI-native): 640 / 768 / 1024 / 1280 / 1536 Pros: Aligns with AI defaults (Tailwind is the most common framework AI generates). 1280 matches the container cap. Cons: Deviates from Marina precedent. 1440 (designer convention) is not in the scale. Option C (Hybrid): 375 / 768 / 1024 / 1280 / 1536 — keeps 375 (mobile design anchor) and 1280 (container cap), drops 1440/1920 in favor of AI-native Tailwind values for the largest steps. SCOPE WHEN DECIDED: • Update tokens/structural/layout.json with chosen breakpoint scale (replacing the existing five-breakpoint set). • Restore a 'Breakpoints' section to the Layout System Storybook page, scoped to component-level responsive use. Make it clear the scale does NOT drive container margins (the container model is breakpoint-agnostic except for the padding step at 768). • Document which breakpoints AI writes naturally vs. which are design-side anchors only. • Audit prior tickets / decisions for any references to the old 375/768/1024/1440/1920 scale that need updating.
